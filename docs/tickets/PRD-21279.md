## Product design

### Goals / Non-goals

**Goals**: ship a read-only MCP connector for one on-prem Yeastar P-Series Appliance-Edition PBX per tenant, exposing: extensions, trunks, call routing (inbound routes, outbound routes, IVRs), and call reports (CDR — call detail records). An Agent with valid per-tenant credentials can list each of these resource types through MCP tools.

**Non-goals** (v1, all assumption-driven since the ticket has no AC — see Open questions):
- No write/configuration operations (create/update/delete extension, trunk, route, IVR). The ticket says "Review", which reads as read-only.
- No real-time call control (the API doc also covers "Control calls" / uaCSTA — out of scope, not asked for).
- No ring groups or queues, even though they sit in the same "Routing & Call Handling" API category as inbound/outbound routes and IVR — the ticket names four groups, not six; ring groups/queues are listed as a follow-up candidate, not silently added.
- No "my reports" (report *definitions*, `myreport/list`) — that endpoint lists saved report configs, not call data; CDR is the capability that actually answers "review ... call reports". Treated as the in-scope one; `myreport/list` is a follow-up candidate.
- No MSPbots platform UI change. This ticket is entirely the MCP server; the connector's credential form is rendered generically by the platform from the `credential_fields` registered at `vendor-register` time (see Tech design § Data & API contract).

### Acceptance criteria AC1..AC10

- **AC1**: Given valid connector credentials are supplied via request headers (`X-Yeastar-Base-Url`, `X-Yeastar-Client-Id`, `X-Yeastar-Client-Secret`), When an Agent calls `tools/list`, Then the server returns exactly 6 tools — `yeastar_list_extensions`, `yeastar_list_trunks`, `yeastar_list_inbound_routes`, `yeastar_list_outbound_routes`, `yeastar_list_ivrs`, `yeastar_list_cdr` — each annotated read-only (`readOnlyHint: true`).
- **AC2**: Given valid credentials, When `yeastar_list_extensions` is called with no arguments, Then the response contains up to 50 extension records (`id`, `number`, `caller_id_name`, `email_addr`, `mobile_number`, `presence_status`, `role_name`) with `has_more` true/false matching whether `total_number` exceeds what was returned.
- **AC3**: Given valid credentials, When `yeastar_list_trunks` is called, Then the response lists configured trunks (`id`, `name`, `type`, `status`, plus `host_port`/`def_outbound_cid` for `peer` trunks or `username` for `account` trunks), same pagination shape as AC2.
- **AC4**: Given valid credentials, When `yeastar_list_inbound_routes`, `yeastar_list_outbound_routes`, or `yeastar_list_ivrs` is called, Then each returns the matching routing configuration — inbound: default/business-hours/after-hours/holiday destinations; outbound: trunk and pattern fields as the upstream API returns them; IVR: the IVR list entries — same pagination shape.
- **AC5**: Given valid credentials, When `yeastar_list_cdr` is called, Then it returns call detail records (`time`, `call_from`, `call_to`, `duration`, `disposition`, `call_type`) sorted by time descending by default, same pagination shape; the tool description states plainly that the upstream API has no server-side start/end time filter, so a caller narrows a time window by paging through time-sorted results and stopping once it reads past the window.
- **AC6**: Given one or more of the three required headers is missing, When any tool is called, Then the server responds 401 and the body lists exactly which header(s) are missing, without making any call to the PBX.
- **AC7**: Given the PBX rejects the client id/secret (`errcode 10005 ACCESS DENIED`) during the internal token exchange, When a tool is called, Then the tool returns `{"error":{"code":"unauthorized","retryable":false}}`. Given a token expires between being obtained and used (`errcode 10004 TOKEN EXPIRED`) on the upstream call, Then the server re-authenticates and retries the upstream call exactly once before surfacing an error.
- **AC8**: Given the PBX returns any other non-zero `errcode`, or the HTTP call to the PBX times out or fails to connect, When a tool is called, Then the server returns one of the fixed error-envelope codes (`not_configured | unauthorized | not_found | invalid_argument | rate_limited | upstream_error`) — never a raw Yeastar `errcode`, never an unhandled exception — and `message` never contains the client secret or an access token.
- **AC9**: Given two concurrent tool calls carrying different header sets (different PBX appliances) on the same running server process, When they overlap in time, Then neither call's credentials or result data leak into the other (request-scoped isolation; verified with a unit test using two concurrent `ContextVar` scopes, since only one physical appliance is available for testing — see Open questions).
- **AC10**: Given a PBX with zero trunks (or zero IVRs, zero inbound routes, etc.) configured, When the corresponding tool is called, Then it returns an empty `items` array with `has_more: false` — not a `not_found` error (per the SOP's "empty is not an error" rule).

### Data & API contract

**Credential headers** (declared in README and in the `vendor-register` call at INT-publish time, modeled on the Oitvoip field shape):

| Header | Required | Meaning |
|---|---|---|
| `X-Yeastar-Base-Url` | Yes | The appliance's API base URL, e.g. `https://192.168.5.150:8088` (HTTPS on 8088 is the vendor default; HTTP on 80 is supported by the appliance but not recommended — see Non-functional) |
| `X-Yeastar-Client-Id` | Yes | OAuth client id from the PBX web portal → Integrations → API |
| `X-Yeastar-Client-Secret` | Yes | OAuth client secret from the same portal screen (masked) |

**Internal token exchange** (not exposed as a tool; done once per incoming MCP request, see § Non-functional on why there is no cross-request token cache):

```
POST {base_url}/openapi/v1.0/get_token
Content-Type: application/json
{"username": "<client_id>", "password": "<client_secret>"}

-> 200 {"errcode":0,"errmsg":"SUCCESS","access_token":"...","access_token_expire_time":1800,
        "refresh_token":"...","refresh_token_expire_time":86400}
```

Every subsequent upstream call appends `?access_token=<token>` (plus the tool's own query params). After the upstream call completes (success or error), the client calls `GET {base_url}/openapi/v1.0/del_token?access_token=<token>` to revoke it immediately — see Non-functional for why this matters given the vendor's 8-concurrent-token cap.

**The 6 tools** (`<vendor>_<verb>_<resource>` naming, all read-only, `limit` default 50 / hard cap 200 per SOP §2.5):

| Tool | Upstream endpoint | Key response fields |
|---|---|---|
| `yeastar_list_extensions(limit=50, cursor=None, sort_by=None, order_by=None)` | `GET extension/list` | `id, number, caller_id_name, email_addr, mobile_number, presence_status, role_name` |
| `yeastar_list_trunks(limit=50, cursor=None, sort_by=None, order_by=None)` | `GET trunk/list` | `id, name, type, status, host_port \| username, def_outbound_cid` |
| `yeastar_list_inbound_routes(limit=50, cursor=None)` | `GET inbound_route/list` | `id, pos, name, default_destination, business_hours_destination, outside_business_hours_destination, holidays_hours_destination` |
| `yeastar_list_outbound_routes(limit=50, cursor=None)` | `GET outbound_route/list` | upstream route fields as returned (trunk, pattern) |
| `yeastar_list_ivrs(limit=50, cursor=None)` | `GET ivr/list` | upstream IVR list fields as returned |
| `yeastar_list_cdr(limit=50, cursor=None, sort_by="time", order_by="desc")` | `GET cdr/list` | `time, call_from, call_to, duration, talk_duration, disposition, call_type, src_addr` |

`limit`/`cursor` map to the upstream `page_size`/`page` (page-number pagination, not a true cursor — `cursor` is implemented as an opaque encoded page number so the tool contract doesn't leak that detail, and so the pagination style can change later as a compatible change). `has_more` is computed from `total_number` vs. `page * page_size`.

**Error mapping** (Yeastar returns HTTP 200 with `errcode` in the body for both success and failure — the client must branch on `errcode`, not HTTP status):

| Yeastar `errcode` | Meaning | MCP error `code` | `retryable` |
|---|---|---|---|
| `10005` (ACCESS DENIED) | bad client id/secret, or token lacks permission | `unauthorized` | false |
| `10004` (TOKEN EXPIRED) on the data call | token expired between acquisition and use | retry once (re-auth), else `unauthorized` | false (after retry) |
| `10009` (OPERATION FAILED) | feature disabled / insufficient permission on PBX | `upstream_error` | false |
| `-1` (FAILURE) / any other non-zero, undocumented code | generic/unknown upstream failure | `upstream_error` | true |
| connection refused / TLS handshake failure / timeout | network/appliance reachability | `upstream_error` | true |
| malformed `limit`/`cursor` caught before the upstream call | — | `invalid_argument` | false |

### Key flow / sequence

```
Agent -> Gateway -> yeastar-mcp /mcp (Header: Base-Url, Client-Id, Client-Secret)
  1. middleware reads 3 headers -> ContextVar; missing any -> 401 (never reaches step 2)
  2. tool handler: api_client.get_token(base_url, client_id, client_secret)
       errcode 0      -> continue with access_token
       errcode 10005  -> return {"error":{"code":"unauthorized","retryable":false}}
       network error  -> return {"error":{"code":"upstream_error","retryable":true}}
  3. tool handler: GET <resource>/list?access_token=...&page=...&page_size=...
       errcode 0      -> map fields, compute has_more, return JSON string
       errcode 10004  -> go to 2 once more (fresh token), retry this call once; still 10004 -> unauthorized
       other errcode  -> map per table above
  4. finally: api_client.del_token(base_url, access_token)  # best-effort, errors logged not surfaced
  5. middleware: ContextVar.reset()
```

### Decisions made by DEV01

No requester was available to ask; these are the first-version choices and their rationale, so they can be revisited explicitly rather than silently assumed later:

- **Picked 6 tools, not a 1:1 mirror of every "Feature Configuration API" endpoint** — ring groups and queues exist in the same upstream category but weren't named in the ticket (Q1); keeping the tool count to what was asked keeps the tool list small (SOP §2.1: tools are capabilities, not an endpoint-for-endpoint mirror) and leaves room under the SOP's ≤20-tool cap for the follow-ups.
- **No cross-request token cache; token fetched and revoked per MCP request** — the alternative (cache the token per appliance for its 30-minute life) would violate the SOP's "no cross-request state" rule (§3.4) since a shared cache keyed only by appliance would leak across whichever tenant/session hits it first; the cost is one extra HTTP round-trip per tool call, accepted as a correctness-over-latency trade.
- **`page`/`page_size` wrapped as `limit`/`cursor` rather than exposed as-is** — keeps the tool contract stable if Yeastar's pagination style changes, and matches the SOP's `list` tool shape (§2.5); alternative (expose `page`/`page_size` directly) was rejected as leaking an implementation detail into the Agent-facing contract.
- **CDR chosen over `myreport/list` for "call reports" (Q2)** — CDR is the only endpoint that returns actual call data; `myreport/list` only lists saved report *names*, which isn't independently useful to an Agent without a "fetch report result" endpoint (not found in the public docs).
- **TLS verification stays on by default, even though the appliance commonly runs a self-signed certificate** — disabling certificate verification by default would be a silent security downgrade for every tenant; instead, a TLS failure surfaces as `upstream_error` (retryable) with a message telling the admin to install a trusted certificate or use the appliance's HTTP port deliberately via `X-Yeastar-Base-Url=http://...` (their choice, not ours).

To change any of these, say so in a comment and move this ticket back to `5b - ready for groom`.

### Non-functional

- **Idempotency/concurrency**: every tool call is a `GET`; no write path exists in v1, so there is no idempotency concern on the Yeastar side. Request-level isolation is enforced via `ContextVar` (SOP §3.3) — see AC9.
- **The vendor caps 8 concurrent valid tokens per third-party application** (`get-access-token.html`). Since this design never caches a token across requests (see Decisions), each concurrent tool call in flight for the *same* appliance holds at most one token for the duration of that one call, then revokes it in a `finally` block. Under heavy concurrent traffic against a single appliance (many tool calls in flight at once before their `del_token` completes), it is possible to approach or exceed the 8-token ceiling; a `get_token` failure at that point is expected to surface as `upstream_error`/`retryable:true` (the vendor's own cap, not a MSPbots bug) rather than crash the tool. Documented as a known limitation, not fixed in v1 — fixing it would require either a shared token cache (which Decisions above rejects on isolation grounds) or client-side concurrency limiting per appliance (a candidate follow-up if it's observed in practice).
- **TLS**: appliances commonly ship a self-signed certificate until an admin uploads a trusted one (`api-request-overview.html` notes the option to upload a certificate, implying it isn't on by default). Verification stays on by default (see Decisions); this is called out in the README's Header table so the connecting admin knows to either install a certificate or point `X-Yeastar-Base-Url` at the HTTP port.
- **No server-side time-range filter on CDR** (`query-cdr-list.html` — confirmed by directly re-reading every query parameter on the page; no `start_time`/`end_time`/equivalent exists). This is a real upstream limitation, not an oversight: the tool description for `yeastar_list_cdr` says so explicitly, and the contract exposes `sort_by="time", order_by="desc"` as the default so a caller narrows a window by paging through time-ordered results, consistent with AC5.
- **Security**: credentials never touch logs, config, or environment variables (SOP §3.1/§3.4, §6/§11); error `message` text is checked (TC-015) to never include the client secret or an access token.
- **Multi-tenant isolation**: this connector serves one PBX appliance per credential set; two tenants pointing at two different appliances are isolated purely by the Header values carried on each request (no shared state exists to leak across them) — see AC9.
- **Observability**: standard SOP logging (§6) — log the upstream `errcode`/HTTP outcome and tool name, never the Header values or the access token.

### Risks & dependencies

- **Risk**: self-signed TLS on the appliance is the common case, which could make most real connections fail verification until the admin installs a certificate. Mitigated by: verification stays on (Decisions), failure surfaces as a clear `upstream_error` rather than a silent insecure fallback, and the README documents the HTTP-port alternative explicitly.
- **Risk**: 8-concurrent-token cap (Non-functional) under unusually high concurrent load against one appliance. Mitigated by: `del_token` in a `finally` block to release tokens promptly; accepted as a known limitation, not engineered around in v1.
- **Dependency**: none on any other PRD or repo. Self-contained new MCP service.
- **Dependency**: a real Yeastar appliance/account for full end-to-end verification — not available to DEV01, not a blocker per SOP, tracked as a manual test case.
